# ルールを開発する

[ドキュメント一覧](../README.md) · [ソース構成](architecture.md) · [開発環境と検証](build.md) · [リリースする](releases.md)

## 検査する動作を決める

実装前に、違反するコードと許可するコードを用意してください。
規則の目的に加え、次の境界を確認します。

- 通常のコード、テストコード、生成コードのどれを対象にするか。
- 対象フレームワークや、参照する型の有無に条件があるか。
- 型の別名、間接継承、partial宣言、複数ファイルでも同じ判定になるか。
- 関連規則を同時に有効にしたときに、相反する修正を求めないか。
- 設定値の省略、不正値、ファイル別の上書きをどう扱うか。

クラス名・メソッド名が同じだけの別の型を誤検出しないよう、型やメンバーの意味が必要な判定にはシンボルを使用してください。

## 診断を定義する

診断ID、メッセージ、カテゴリ、重大度を `Contracts/Diagnostics` に定義してください。
メッセージには、問題と修正方法を簡潔に記載します。
相反する選択式の規則は既定で同時に有効にしないでください。

| 系統 | 診断ID |
| --- | --- |
| Core | `RAW` に続く番号。関連する選択式の規則では末尾の英字も使用 |
| MVVM | `RAWMVVM` に続く番号 |
| Razor | `RAWRAZOR` に続く番号 |

公開済みのIDを別の意味に使い回さないでください。
新しい規則と公開済み規則の変更は、[リリース情報](releases.md#診断のリリース情報を更新する)へ記録します。

## 修正対象を示す

診断位置は、利用者が修正する箇所をできるだけ狭く示してください。

| 検査するもの | 診断位置の目安 |
| --- | --- |
| 型・メンバー・変数の命名 | 識別子 |
| メソッドの呼出し | メソッド名 |
| 属性 | 属性名、または問題のある引数 |
| 不要な空白・空行 | 対象の空白や改行 |
| クラス全体の行数 | クラス名 |
| ファイル構成や集計結果 | 違反を示す代表の宣言 |
| 設定ファイル内の値 | `AdditionalText` の実際のファイル位置 |
| Razorの利用者コード | 生成C#から対応する元ファイルの位置 |

Razorでは、識別子だけが元画面に対応する生成プロパティがあります。
`@inject` 由来の宣言などを、利用者が書いたメンバーと混同しないでください。

## 実装する

解析の入口、対象判定、診断定義の責務を分け、既存の構成へ追加してください。
構文の種類だけで判定できるものは構文解析を使い、型や引数の意味が必要なものは意味情報や操作情報を使ってください。

共通の実装規約は次のとおりです。

- 日本語のXMLコメントで役割を記述する。
- クラスを350行以内に収め、目的のないプロジェクト分割やpartial分割を増やさない。
- 日時には `DateTimeOffset` を使用し、JSONには `System.Text.Json` を使用する。
- `NoWarn` に抑制IDを追加しない。必要な例外には、日本語の理由コメントと `Justification` を付けた `SuppressMessage` を使用する。
- 並列解析で共有する状態は、更新方法と有効範囲を明確にする。
- 読み取り可能な設定を、独自の静的キャッシュへ固定しない。

## テストする

診断IDを扱うテストクラスとファイル名は、`RAW120BPrivateFieldNamingAnalyzerTests.cs` のようにIDで始めてください。
補助クラスはこの命名の対象外です。

テストでは実際にC#をコンパイルして、次を確認してください。

1. 違反するコードで、想定したID・重大度・位置の診断が出る。
2. 修正したコードと対象外のコードでは、その診断が出ない。
3. 別名、生成コード、複数ファイル、設定変更など、変更に関係する境界でも判定が安定する。
4. 関連する複数の規則を併用しても矛盾しない。

ソース文字列の照合や、別のテストを呼ぶだけの入口を追加して、挙動の検証に代えないでください。
パッケージ構成やRazorの生成処理が関係する場合は、[実際の利用先での確認](build.md#実際の利用先で確認する)も必要です。

## 文書を更新する

利用者が確認する規則は `docs/rules`、設定は `docs/guides/configuration.md` に記載してください。
NuGetパッケージのREADMEには概要と導入方法を置き、詳細なルール一覧は複製しません。
文書には現在の使い方と必要な制約を記載し、移行経緯や作業日誌は追加しないでください。
